    Next to a DUT¶

    The first hour on a disconnected machine wired to the device under test: prove the tool works before the DUT is involved, then pin down a recording format you do not yet know.

    Before the DUT¶

    Install as in Installation, offline if need be. Then run the two checks in this order. They separate my install is broken from my recording is odd, and neither needs the DUT, a network or SoapySDR.

    1. The toolchain. The test suite: everything passes with one documented skip (Quickstart, step 2).
    2. The instrument. tools/probes/probe_replica_placement.py. Every number should be zero. The two rows to read are band-limited / place, which must be 0.0000, and point / res_code, also 0.0000, the old placement rule, which is there to show what a false pass looks like.

    The second check matters because a ripple at one cycle per sample of delay traversed is the signature of a defective generator interpolator and equally the signature of an instrument that cannot place its replica between samples. This tool was once the second (Replica placement).

    When you do not know the recording's format¶

    This is the likely first obstacle. A misread format is the worst kind of wrong, because it produces plausible numbers rather than an error. The rule: a format is declared, then cross-checked, never inferred.

    tools/identify_format.py narrows the candidates so the declaration you write is an informed one:

    python tools/identify_format.py RECORDING.bin --fs 5115000 --duration 120

    It prints every plausible (dtype, interleave) with the sample count, duration, level statistics, DC fraction and I/Q imbalance each implies. Work through it in this order.

    1. Bytes per complex sample, from arithmetic. If you know the rate and duration, size / (fs × duration) is the strongest discriminator there is, and it should come out a whole number. If it does not, one of the two is wrong or the file has a header, and the remainder tells you how big.

    2. Which dtype of that width, from statistics. A wrong one is usually loud: int8 bytes read as float32 give NaN, read as int32 an rms of 1.5 × 10⁸. Look for a plausible level spread with the peak below the type's limit.

    3. The sense bit, and there is only one. Verified exactly:

    read(qi)  ==  1j * read(iq, spectral_sense="inverted")     # max difference 0.0

    So interleave: iq versus qi and spectral_sense: normal versus inverted are the same one-bit ambiguity, differing by a constant 90°, which the tool removes anyway as the carrier-phase origin. Do not sweep them as two unknowns: pick one field to carry the bit. At zero IF, acquisition cannot resolve it (both senses acquire at the same C/N0 and code phase; only the Doppler sign flips). A capture long enough to decode ephemeris can, from Doppler sign against elevation trend; that worked on 10 of 10 satellites on the first real recording.

    4. Confirm by acquiring. This is the check that decides. A wrong dtype does not acquire at all.

    gnss-vsa validate capture.toml
gnss-vsa spectrum capture.toml     # works even when nothing acquires
gnss-vsa run      capture.toml

    Declare the two fields that default to unknown¶

    Neither is inferred, so someone has to say:

    • source_chain: "digital" for a generator writing straight to disk, "rf" if an analog chain, and therefore thermal noise, is in its history. On a digital source there is no thermal floor, everything above the quantization step is the generator, and C/N0 stops meaning carrier-to-noise density. Set it and the tool qualifies the number for you.
    • spectral_sense: see above. "unknown" is a legitimate answer, and better than a guess.

    Check the quantization headroom¶

    On a digital source the quantization step is the noise floor, so unused range is dynamic range given away. One 120 s int8 simulator recording spanned exactly −26 to +26 on I and Q: every level occupied, so dither was fine, but 13.8 dB of the int8 range unused. If your DUT writes int8, check the same number before recording anything long.

    What to bring back¶

    • the sidecar you declared, and how you established it
    • gnss-vsa validate output for the first capture
    • the HTML report, or at least its Notes and assumptions section
    • the parquet store if it is small enough, plus the manifest: together they are enough to re-run analyze without re-correlating
