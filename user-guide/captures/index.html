    Describing a capture¶

    Two files: a sidecar JSON per recording says what the file is, and one manifest TOML says how the recordings compose.

    A capture is an N × M grid: N elements (RF outputs of the generator under test) by M carriers (L1, L5, E1, …), one recording per cell. Recordings carry no timestamps: everything is measured blind, relative to sample 0. Each carrier has its own LO and possibly its own sampling rate, so those are per-carrier properties, not capture-wide ones.

    The sidecar¶

    What your recording pipeline should emit beside each file. Its job is to remove guesswork about the bytes.

    {
  "fs_hz": 12000000, "f_center_hz": 1575420000, "f_if_hz": 0,
  "dtype": "complex64", "interleave": "iq", "spectral_sense": "unknown",
  "element": 1, "carrier": "L1"
}
    Field Values
    dtype complex64, complex128, int8, int16, int32, float32, float64
    interleave iq, qi or real
    byte order, header size, start offset all supported

    Anything outside that is a small addition to the reader, but it must be known rather than assumed. A misread format produces plausible numbers, which is the worst kind of wrong. If you do not know the format yet, see Next to a DUT.

    Two fields default to "unknown" and are worth setting deliberately:

    Field Why it matters
    spectral_sense Whether the spectrum is as recorded or conjugated. Get it wrong and every Doppler sign inverts. A capture long enough to decode ephemeris can measure its own sense.
    source_chain "digital" marks a source with no thermal noise, which changes how C/N0 must be read (see Numbers not to quote).

    The manifest¶

    The one thing no single recording can know about itself: how the files compose.

    name = "run-2026-07-27"
reference_element = 1          # what every other element is differenced against

[[carriers]]
name = "L1"
fs_hz = 12000000.0
f_if_hz = 0.0
signals = ["L1CA"]
prns = [1, 5, 12, 17]

[[cells]]
element = 1
carrier = "L1"
path = "element1_L1.bin"

[[cells]]
element = 2
carrier = "L1"
path = "element2_L1.bin"
start_sample = 0               # be explicit: a differing start silently offsets every comparison

    Start alignment across recordings is an assumption, not a fact. Each file starts at its own sample 0, and a recording cannot detect on its own that it started late. start_sample defaults to 0, and the report says that alignment was assumed rather than measured.

    A single-element capture is a first-class case, not a degenerate one. Declare one cell and everything except diff runs.

    Supported signals¶

    17 signal components across GPS, Galileo, BeiDou and QZSS, each measured to injected truth. The names below are the ones to put in signals.

    Constellation Signal signals names Measured on
    GPS L1 C/A L1CA synthetic signals and simulator recordings
    GPS L5 L5I (data), L5Q (pilot) synthetic signals
    Galileo E1 E1B (data), E1C (pilot) synthetic signals; E1B also on simulator recordings
    Galileo E5a E5AI (data), E5AQ (pilot) synthetic signals
    Galileo E5b E5BI (data) synthetic signals
    Galileo E6 E6B (data), E6C (pilot) synthetic signals
    BeiDou B1I B1I synthetic signals
    BeiDou B2I B2I synthetic signals
    BeiDou B2a B2AD (data), B2AP (pilot) synthetic signals
    BeiDou B3I B3I synthetic signals
    QZSS L6 L6D, L6E synthetic signals

    How each signal was measured¶

    Synthetic signals. Every signal above is built as a test signal with a known code offset and Doppler: 200 ms at 48 dB-Hz, with the secondary code applied where the signal has one. The acquisition engine finds it on a coarse 4-bit copy, and the instrument then measures the original samples. Over four noise draws per signal, every one acquired every time, measured code offset to 0.003–0.030 sample RMS and Doppler to within 0.05 Hz. A regression test holds every signal to that result. L1 C/A is validated in more depth than the rest (Key figures).

    Simulator recordings. L1 C/A and E1B have also been measured on recordings from a real GNSS simulator, which is where a generator's defects show. The other signals have not yet been, and are the next to take there.

    One caveat on E1B. It is correlated together with its pilot by default, and still carries a residual pilot bias of 0.05–0.09 m on some satellites, so L1 C/A remains the signal to measure with.

    Coming: long-code signals¶

    Constellation Signal signals names Code period
    GPS L1C L1CD, L1CP 10 ms
    GPS L2C L2CM, L2CL 20 ms, 1.5 s
    BeiDou B1C B1CD, B1CP 10 ms

    A code this long cannot be acquired on its own. It needs a short-code signal from the same satellite, in the same receiver run, to hand over its Doppler: L2C from L1 C/A, B1C from B1I. That arrives with the carrier packer (Status and roadmap).

    A signal not listed on this page has not been considered. validate reports coverage per signal, since the code period sets how many epochs a recording yields.

    What validate checks¶

    gnss-vsa validate capture.toml

    It checks the manifest, the recordings and the known traps, and reports each problem with a severity:

    • an error means the tool would measure wrongly, and stops the run;
    • a note is true, legal and reportable: a sparse PRN grid, an alignment nobody measured.

    Exit status is 1 if any error is present and 0 otherwise. It also answers coverage per signal, because a code period is 1 ms on L1 C/A and 4 ms on E1B, so one recording can be long enough for one and too short for the other. It names which detectors the capture can feed, and why the others' minimums are what they are.
