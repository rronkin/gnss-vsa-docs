    Reading the output¶

    A self-contained HTML report to read, and a parquet store to query. Read the report's notes before any number.

    The HTML report¶

    Sections appear in this order, and the order is the reading order:

    1. Capture: what was measured, with what options. This is provenance; keep it.
    2. Notes and assumptions: everything the tool wants to qualify. Read this before any number below it.
    3. Acquisition and Measurements (open-loop): the pointer, then what the tool's own correlator made of it. The second is the one to quote.
    4. Spectrum: per cell, plus a PSD figure with every cell on one axis, each in dB relative to its own mean power.
    5. Differences and Difference series: N > 1 only. The alignment, then the inter-element differences.
    6. Detector sections: one table per detector, including the rows that say a detector was skipped, and why.
    7. Stability: Allan and time deviation against averaging interval.
    8. Series: the observables themselves, stacked per signal.

    The store¶

    Parquet on disk, DuckDB on top. Reach for it when the report is not the shape of your question:

    gnss-vsa query store "SELECT element, sat, coff_samples, dop_hz FROM measurements"
gnss-vsa query store "SELECT * FROM ripple WHERE detected"
gnss-vsa query store "SELECT sat, column, status, note FROM quantization WHERE status <> 'ok'"

    Tables: acquisitions, measurements, observables, spectrum, psd, differences, difference_summary, alignment, and one per detector: quantization, ripple, step_scans, steps, stability, deviation.

    On disk it is a directory that anything reading parquet can open (pandas, Polars, DuckDB, parquet-tools). Nothing in it is private; gnss-vsa query is a convenience over read_parquet, not a gate.

    store/
├── acquisitions/capture=<name>/e1_L1.parquet   # one partition per (element, carrier)
├── observables/capture=<name>/e1_L1.parquet
├── measurements/capture=<name>/e1_L1.parquet
├── spectrum/capture=<name>/part.parquet        # keyed by cell already; written whole
├── psd/capture=<name>/part.parquet
├── ripple/capture=<name>/part.parquet          # detector over the elements
├── ripple/capture=<name>/differences.parquet   # ... and over the differences
└── _done/<32 hex>.json                         # what has been computed, and why

    Each detector writes two parts, because a per-element finding and an inter-element one are different claims and re-running one must not rewrite the other. The series column says which a row is: element or difference.

    import duckdb
duckdb.sql("SELECT * FROM read_parquet('store/observables/**/*.parquet', "
           "hive_partitioning = true)")

    The observable series¶

    The raw material every detector consumes, keyed by (element, carrier, sat, sig, arc):

    Column Meaning
    time_s Epoch time from the start of the capture
    coff_samples Code offset in samples, unwrapped across the code period
    phase_cyc Carrier phase in cycles
    dop_hz Per-epoch Doppler, differentiated from phase_cyc: noisy by construction
    cn0_dbhz Carrier-to-noise density, over a 20-epoch window

    measurements holds the correlator's per-signal results, including the discriminator_slope each code offset was converted with.

    What a re-run does to the store¶

    When a stage runs, it replaces the partitions it owns rather than merging into them, so a re-run that finds less leaves less behind. Once both acquire and correlate have run, measurements holds exactly one row per acquired signal. One query says whether a store is sound, and which way it is wrong:

    gnss-vsa query store "SELECT (SELECT count(*) FROM acquisitions WHERE acquired) AS acquired,
                             (SELECT count(*) FROM measurements) AS measured"

    measured above acquired means stale rows; below it, a correlate that has not caught up with the census.

    Deleting the store is not the way to fix a result. It also discards _done and every archived series, so the next run re-correlates from the start, which takes minutes to hours on a long capture, for what --force on one stage does in seconds.

    What actually ran¶

    _done/ holds one JSON file per completed unit of work: the stage, the cell, the recording, the effective options and the acquisition engine's commit. It is the record of why a number is what it is.

    python -c "import glob, json; [print(json.load(open(p))) for p in glob.glob('store/_done/*.json')]"

    Inputs are addressed by content, not by name: a recording edited in place produces a different key and is correctly re-measured. A changed argument does the same, so a stage re-running after an edit is the cache working, not a fault.
